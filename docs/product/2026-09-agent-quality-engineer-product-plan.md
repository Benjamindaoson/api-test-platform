# Agent Quality Engineer：产品计划

## 1. 产品命题

**Agent Quality Engineer（AQE）** 是面向企业内部 Agentic AI 应用的无人值守 AI 测试工程师。

它在每次代码、Prompt、模型、知识库、检索配置或工具定义变更后，自动决定该测什么、在隔离环境中执行测试、评估结果、归因失败，并输出可用于发布决策的证据。

**不做**通用测试管理平台，也不做只展示 Trace 的 Eval Dashboard。

## 2. 问题陈述

### 目标用户

- 主要用户：负责企业内部 RAG/工具调用 Agent 的 AI 工程师与质量工程师。
- 决策用户：AI 平台负责人、研发负责人、发布负责人。
- 消费者：PR 审核人、编码 Agent、事故复盘人员。

### 他们的真实问题

传统测试难以覆盖 Prompt、模型、知识库、检索策略和工具调用的组合变化。一个 API、页面和单元测试都通过的版本，仍可能出现幻觉、引用失真、错误工具调用、越权、Prompt injection 或多轮状态错误。

团队今天通常靠零散脚本、人工抽样、通用 Eval 平台和发布后的日志发现问题。问题不在于缺少单项评分，而在于没有把**变更、测试计划、Agent 轨迹、质量结论和发布决策**连成闭环。

### 成功定义

在无人手工触发每次测试的前提下，系统针对变更生成可复验结论，并且能以历史故障回放、变异测试和稳定性测试证明其测试效果没有退化。

## 3. 产品边界

### v0.1 聚焦

企业内部、英文或中文均可的 **RAG + 只读工具调用 Agent**：知识助手、客服 Copilot、研发知识助手、内部流程问答。

### v0.1 不做

- 可造成不可逆副作用的 Agent 自动执行；
- 多 Agent 开放式长任务；
- 自动修改、合并或推送业务代码；
- 通用可视化测试管理、CRM 或工时功能；
- 声称“无 Bug”或“绝对安全”。

## 4. JTBD

> 当我准备合并或发布一个 Agent 应用的变更时，我希望系统自动证明它仍然能正确检索、可靠回答、安全使用工具并在异常条件下拒绝或降级，从而不必依赖人工抽样和上线后的事故发现回归。

## 5. 机会树

```text
结果：缩短获得可信 Agent 发布结论的时间
├─ 不知道变更会破坏什么
│  ├─ 变更影响分类（代码 / Prompt / 模型 / RAG / 工具）
│  └─ 风险驱动的测试计划
├─ 不知道回答是否真的可信
│  ├─ Grounding、正确性、拒答和引用评估
│  └─ 历史事故与变异测试集
├─ 不知道 Agent 是否会安全行动
│  ├─ 工具轨迹、参数和权限策略评估
│  └─ 工具模拟器与故障注入
└─ 不知道是否应该发布
   ├─ 版本化证据包
   └─ 策略驱动的放行、阻断或升级结论
```

## 6. 差异化定位

现有 Eval/Observability 工具已经能够管理数据集、Trace 和指标。AQE 不复制它们的 Dashboard，而在它们之上或旁边完成：

```text
变更检测 → 自动测试设计 → 对抗执行 → 版本比较 → 发布门禁 → 修复复验
```

产品的长期数据资产是 **Release Evidence Graph**：

```text
Commit / Prompt / Model / Index / Tool schema
↔ test case / evaluator / trace
↔ quality verdict / defect / repair / re-verification
```

## 7. 三阶段路线

| 阶段 | 目标 | 核心能力 | 不做 |
| --- | --- | --- | --- |
| 1. RAG Release Gate | 让 RAG 变更可自动发布判断 | 数据集、Grounding、正确性、拒答、Prompt injection、版本比较、证据包 | 自动写代码、复杂工具副作用 |
| 2. Tool-Using Agent QA | 让工具调用 Agent 可安全验证 | 工具选择/参数/轨迹、模拟器、超时与重复调用、权限策略 | 开放式多 Agent |
| 3. Autonomous Release Engineer | 让质量闭环持续学习 | 变更风险预测、历史缺陷回放、修复任务、复验、质量知识图 | 无策略的自动发布 |

## 8. 最重要的待验证假设

**假设 H1：** 对企业内部 RAG Agent 的一次变更，AQE 能在规定时间和成本预算内，自动发现人工抽样或现有回归遗漏的高风险退化。

H1 尚未被验证。最小验证方法：选取一组已脱敏的历史 PR、真实缺陷与知识库变更，在隐藏结果的情况下对比现有 CI/Eval 流程和 AQE 的发现率、误报率、耗时及每次运行成本。

## 9. 决策指标

- 已知高严重度回归的发现率；
- 误报率与不可判定率；
- 从变更到质量结论的时间；
- 每个变更的测试成本；
- 被策略自动放行、自动阻断和升级处理的比例；
- 测试集对新失败模式的增长速度。

## 10. 风险与约束

| 风险 | 处理原则 |
| --- | --- |
| LLM Judge 不稳定或有偏 | 确定性检查优先；Judge 使用版本化 rubric、校准集和抽样复核 |
| Trace 含敏感数据 | 采集前与存储前两层脱敏；最小化、访问审计、保留期限和删除链路 |
| 生成测试造成噪音 | 每条生成测试必须有失败模式、风险来源和评估器证据 |
| 错误发布结论 | 策略分级；高风险变更默认升级而非盲目放行 |
| 范围过宽 | v0.1 仅针对 RAG + 只读工具调用 Agent |
